# Demo runbook

Owner: Windows 2 for presentation text; Mac owners operate real backend/model/capture services. This is a proposed sequence, not proof of completed features.

## Before presenting

- Pin the tested model/runtime and prepare dependencies locally. Test without event internet if local-only is claimed.
- Use a disposable demo repository and declared synthetic private data; never use a real account token or personal clipboard content.
- Close private clipboard sources and enable capture only for the demonstration, with visible consent/status.
- Record the actual client version and tested adapter paths. Show unsupported paths explicitly.
- Ensure fixture mode cannot be mistaken for live mode. The recording of a demo, if made for submission, is not a diagnostic input or product screen-monitoring feature.
- Reset only the dedicated demo snapshot. Do not run destructive reset commands on a developer's active repository.

## Privacy and clipboard story

1. Explain the coding task: diagnose a login exception.
2. Enable text clipboard protection. Copy a fresh prepared log containing useful error facts and synthetic sensitive values; vary content from prompt examples.
3. Show real CHECKING/current-version state and the redacted local finding. Confirm Gemma performed contextual analysis where needed.
4. Use Copy cleaned text explicitly; show a safe preview and preserved debugging details. Do not display the original token in the public audit panel.
5. Send through the verified adapter/reference gate. Inspect the actual local test receiver payload to prove the supported route received the cleaned version.
6. Show a protected read denied and a benign input retained.
7. Explain that clipboard observation does not stop every unrelated app paste; show coverage status rather than a universal-protection claim.

## Backend repair story, if implemented

1. Use a named API/test signal to demonstrate a small real regression; show the trusted baseline failing.
2. Click Investigate now or Enter idle mode. Evidence comes from source, diffs, selected structured logs, API probes and test output.
3. Show real selected tools, concise observations, the candidate source diff and independent verification.
4. Confirm the developer's originals are unchanged before review.
5. Edit an original file to show stale rejection; alternatively apply a fresh reviewed candidate and show the tested operation.

No screenshot, screen recording, video understanding or visual bug diagnosis is used for the repair pipeline. No scripted successful patch is substituted for a failed model attempt.

## Failure branch

If the model times out, show held privacy input or UNRESOLVED repair. If a client adapter is unsupported, demonstrate the actual reference gate and label client coverage incomplete. If resource pressure occurs, pause repair and keep the foreground privacy route held until it can inspect safely. Never silently switch models or to fixtures.

## Submission wording template

"DevGuard uses local Gemma 4 E4B to analyse contextual sensitivity and investigate backend failures. Deterministic policy and independent tests enforce supported actions. The prototype supports [actual verified clipboard host and client paths]. We measured [actual counts and timings]. Remaining limitations: [actual gaps]."

List privacy/clipboard and repair completion separately. Include model/runtime licence notices, hardware, setup, public repo URL and a reproducible evaluation record. Confirm whether the organiser accepts both categories; local Gemma use and public code do not prove multiple-category eligibility.
